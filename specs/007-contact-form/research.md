# Research: Contact Form and Message Retrieval

**Feature**: `007-contact-form` | **Date**: 2026-09-29 | **Plan**: [plan.md](./plan.md)

Every decision below was checked against current documentation, not memory. Cloudflare facts
come from developers.cloudflare.com (fetched 2026-09-29) and from the installed `wrangler`
4.143.0 / `miniflare` sources in `node_modules`. Astro facts come from the Astro Docs MCP
(`astro-docs`), cited by page. Package versions come from the npm registry on 2026-09-29.

## R1. Where the contact API runs: a plain Worker entry beside the static assets

- **Decision**: Add `main: "worker/src/index.ts"` to `wrangler.jsonc` and set
  `assets.run_worker_first: ["/api/*"]`. The Worker handles `fetch` for `/api/*` only and
  `scheduled` for the retention cron. There is no `ASSETS` binding: the Worker never serves a
  page. Every other path stays a static asset request, which is free and unlimited.
- **Rationale**: Cloudflare documents `run_worker_first` as a boolean or an array of up to 100
  glob patterns (`*` matches deeply, `!` negates) that "runs the Worker first only for specific
  routes while letting other requests follow the default asset-first behavior"
  (developers.cloudflare.com/workers/static-assets/binding/). "Requests to static assets are
  free and unlimited. Requests to the Worker script … are billed according to Workers pricing"
  (…/static-assets/billing-and-limitations/). This is exactly Constitution Principle VIII's
  "Only `/api/*` invokes Worker code".
- **First-party options considered (Principle IV)**:
  - `@astrojs/cloudflare` adapter with an on-demand `src/pages/api/contact.ts` endpoint. Astro's
    own guide says "If you're using Astro as a static site builder, you don't need an adapter"
    (docs.astro.build/en/guides/integrations-guide/cloudflare/). The adapter would bundle the
    Astro server runtime into the Worker, and its routing falls back to the Worker for any
    unmatched path ("If no match is found, this will fall back to the Worker for on-demand
    rendering", same page, "Routes"), which breaks the current `not_found_handling: "404-page"`
    static behaviour and makes 404s billable Worker requests. It also has no first-party
    `scheduled` handler: a cron needs a custom entry anyway (same page, "Changed: Custom
    entrypoint API"). Rejected: it adds a dependency and server rendering without meeting the
    requirement better.
  - Astro Actions: need an adapter and on-demand rendering (docs.astro.build/en/guides/actions/).
    Rejected for the same reason.
  - Pages Functions: the site is on Workers static assets, not Pages. Not applicable.
  - Result: a small hand-written Worker is the Cloudflare first-party option (Workers + static
    assets), and no Astro first-party option meets "static site plus `/api/*` plus cron" without
    server rendering.
- **Headers**: `_headers` rules "are not applied to responses generated by your Worker code,
  even if the request URL matches a rule" (…/static-assets/headers/). The Worker therefore sets
  its own headers on every response: `Content-Type: application/json; charset=utf-8`,
  `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `X-Robots-Tag: noindex`,
  `Referrer-Policy: no-referrer`, `Strict-Transport-Security: max-age=31536000`. A unit test pins
  this list against `public/_headers` so they cannot drift apart silently.

## R2. Storage: two D1 databases, location hint `wnam`, Wrangler migrations

- **Decision**: Two D1 databases, `contact` (production) and `contact-preview` (preview), both
  created by Don with `pnpm exec wrangler d1 create <name> --location wnam`. One migrations
  directory, `migrations/`, shared by both bindings. The binding name is `DB` in both
  environments, so the Worker code never branches on environment.
- **Rationale**: Valid hints are `wnam`, `enam`, `weur`, `eeur`, `apac`, `oc`; "Location hints
  cannot be changed after database creation", and a hint "does not guarantee that D1 runs in
  your preferred location" (…/d1/configuration/data-location/). The spec's clarification
  confirms Western North America. Wrangler-managed migrations are the first-party schema tool
  (`wrangler d1 migrations create|list|apply`).
- **Database IDs are required in config**: when a D1 binding omits `database_id`, Wrangler's
  automatic provisioning creates the database on deploy and writes the ID back
  (…/wrangler/configuration/, "D1 databases"). That would create a database with **no** location
  hint. The plan therefore requires both IDs to be committed before any remote deploy, and a
  config test fails if either binding lacks a `database_id` or uses a placeholder.
- **Checking the location**: the documented `GET /accounts/{id}/d1/database/{uuid}` response
  lists `uuid, name, created_at, file_size, jurisdiction, num_tables, read_replication, version`
  and no location field (developers.cloudflare.com/api/resources/d1/subresources/database/methods/get/).
  The API does return a `running_in_region` value in practice, but it is not in the published
  schema. Decision: `setup:check` confirms the region from `running_in_region` when present and
  equal to `WNAM`; when the field is absent it reports **missing** ("the region could not be
  confirmed") rather than passing. It never passes without positive evidence. Implement must
  confirm the field against a real response during the walkthrough and adjust only the parser,
  not the fail-closed rule.
- **Alternatives considered**: KV (no SQL, no exact counting for rate limits, eventual
  consistency); Durable Objects SQLite (more moving parts than one table needs); one database
  with an `environment` column (violates Principle VII "stored separately" and FR-017).

## R3. Keeping preview messages separate: a `preview` Wrangler environment and its own Worker

- **Decision**: Add `env.preview` to `wrangler.jsonc`. It deploys as a separate Worker,
  `dcc-web-preview`, bound to `contact-preview`, with its own secrets and its own cron. The
  production Worker `dcc-web` is bound to `contact`. Branch previews move from `dcc-web` to
  `dcc-web-preview`.
- **Why a separate Worker, not per-version bindings on `dcc-web`**: bindings belong to a Worker
  version, so a preview version of `dcc-web` could bind `contact-preview`. But secrets belong to
  the Worker and every new version inherits them, so previews would share production's
  `CONTACT_READ_TOKEN` and `IP_HASH_SALT`. That breaks FR-024 ("Production and preview MUST use
  different access keys") and would let unmerged branch code read the production token. A
  Worker's cron also runs only its active deployment, so the preview database would never be
  cleaned. A Wrangler environment is Cloudflare's documented way to get a separate Worker with
  separate bindings and secrets ("a Worker project named `my-worker` with an environment `dev`
  would deploy as a Worker named `my-worker-dev`"; secrets are set with
  `wrangler secret put <KEY> --env <env>`; developers.cloudflare.com/workers/wrangler/environments/).
- **Inheritance**: `main`, `compatibility_date`, `assets`, `triggers`, `observability`,
  `workers_dev` and `preview_urls` are inheritable; `vars` and `d1_databases` are not and must be
  repeated in `env.preview` (…/wrangler/configuration/). The plan repeats `triggers` and
  `secrets.required` in `env.preview` as well, so each environment reads completely on its own.
- **How Workers Builds selects the environment**: Workers Builds requires the dashboard Worker
  name to match the config `name`, except that "a Worker named `my-worker-staging` on the
  dashboard can be deployed from a repository that contains a Wrangler configuration file with
  … `name = my-worker` and `[env.staging]` using the deploy command `npx wrangler deploy --env
  staging`" (…/workers/ci-cd/builds/troubleshoot/). Wrangler enforces this with
  `WRANGLER_CI_OVERRIDE_NAME`: in the installed 4.143.0 source (`mergeSharedConfigArgs`), when
  the CI-provided name differs from the resolved name, Wrangler **overrides to the CI name**. So
  a `--env preview` command run by the `dcc-web` connection would silently upload to `dcc-web`
  with production secrets. Decision:
  1. `dcc-web-preview` gets its own Workers Builds connection to the same repository. Its
     production-branch and non-production-branch deploy commands are both
     `pnpm run deploy:preview`.
  2. The `dcc-web` connection turns **off** non-production branch builds, and its production
     deploy command changes from `pnpm exec wrangler deploy` to `pnpm run deploy:production`.
  3. `scripts/deploy/preview.ts` refuses to run when `WRANGLER_CI_OVERRIDE_NAME` is set to
     anything other than `dcc-web-preview` (fail closed), so a misconfigured connection can
     never upload preview code with production secrets or bindings.
- **Preview deploy steps** (`pnpm run deploy:preview`, run by `dcc-web-preview`'s builds):
  1. `wrangler d1 migrations apply contact-preview --remote --env preview`
  2. `wrangler deploy --env preview`. This keeps the preview Worker's active deployment current,
     registers its cron (`versions upload` does not apply triggers) and gives the cron a real
     `scheduled` handler.
  3. On a non-`main` branch only: `wrangler versions upload --env preview --preview-alias <alias>`.
     This gives the stable per-branch address that `astro.config.mjs` already computes. On
     `main` the script stops after step 2.
- **Production deploy steps** (`pnpm run deploy:production`, run by `dcc-web`'s builds on
  `main`): `wrangler d1 migrations apply contact --remote`, then `wrangler deploy`.
- **Preview address**: previews move to `https://<alias>-dcc-web-preview.drc-dev.workers.dev`.
  `setup/config.json` gains `previewWorkerName: "dcc-web-preview"`. `src/lib/site-origin.ts`
  uses it for non-`main` branches, and its maximum alias length becomes
  `63 - "-dcc-web-preview".length` (47). This branch's alias is `br-007-contact-form`.
- **Migrations before code**: both scripts apply migrations before deploying. So every
  migration must be additive and backward compatible with the code already running. A config
  test checks that each migration file only uses `CREATE TABLE`, `CREATE INDEX` or
  `ALTER TABLE … ADD COLUMN` unless a plan explicitly allows otherwise.
- **Alternatives considered**: removing `WRANGLER_CI_OVERRIDE_NAME` inside the script so one
  connection can deploy both Workers. This depends on an undocumented variable's behaviour and
  would defeat a platform safety check. Rejected in favour of the documented
  "separate Worker per environment" setup.

## R4. Local development and E2E: `wrangler dev`, not `astro dev`

- **Decision**: Keep Playwright's existing `wrangler dev --ip 127.0.0.1 --port 4321` web server,
  which serves the production build plus the Worker exactly as Cloudflare will. Before it
  starts, the web-server command runs
  `wrangler d1 migrations apply contact --local --persist-to .cache/e2e-state` on a freshly
  emptied state directory, then `wrangler dev --persist-to .cache/e2e-state --env-file
  tests/fixtures/worker/e2e.env`.
- **Rationale**: `astro dev` without an adapter cannot run the Worker at all, and adding the
  adapter is rejected (R1). `playwright.config.ts` already documents that E2E runs "against the
  production build served by Cloudflare's own local runtime (`wrangler dev`)". Wrangler 4.143.0
  supports `--env-file` ("Path to an .env file to load") and `--persist-to`.
- **Test secrets**: `tests/fixtures/worker/e2e.env` is committed and holds only public test
  values: Turnstile's documented always-pass secret `1x0000000000000000000000000000000AA`
  (developers.cloudflare.com/turnstile/troubleshooting/testing/), plus a clearly fake
  `CONTACT_READ_TOKEN` and `IP_HASH_SALT` that exist nowhere else. The file is not matched by
  `.gitignore`'s `.env` / `.env.*` patterns. Secretlint must stay green; if it flags the file,
  the file is added to `.secretlintignore` with a comment.
- **Per-test rate-limit isolation**: every E2E submission comes from 127.0.0.1, so they would
  share one rate-limit bucket. Miniflare's entry worker sets `CF-Connecting-IP` from the socket
  **only when the request does not already carry one** (installed miniflare
  `workers/core/entry.worker.js`). E2E tests therefore add a unique documentation-range address
  (`203.0.113.x`) to `/api/contact` requests with `page.route`. At the Cloudflare edge the header
  is always set by Cloudflare, so clients cannot spoof it in production.
- **Turnstile in E2E**: the form is built with the always-pass test sitekey
  `1x00000000000000000000AA` ("Dummy sitekeys can be used from any domain, including on
  `localhost`"), and the Worker verifies against real siteverify with the always-pass test
  secret, so the whole journey runs through Cloudflare's own code path. The "check cannot load"
  edge case is covered by aborting `https://challenges.cloudflare.com/**` with `page.route`.
  Service-unavailable and rate-limited UI states are covered with `page.route` fulfilling 503
  or 429 on `/api/contact`, because the server side of both is covered in integration tests.
- **CI dependency**: E2E now reaches `challenges.cloudflare.com`. GitHub-hosted runners have
  network access. This is recorded as a known flake source (plan Risks), with Playwright's
  existing `retries: 0` unchanged.

## R5. Worker tests: Cloudflare's Vitest integration (`@cloudflare/vitest-plugin`) in its own workspace package

- **Decision**: Use `@cloudflare/vitest-plugin` (the current name; it replaces
  `@cloudflare/vitest-pool-workers`, "The package API and Vitest configuration are unchanged",
  …/vitest-integration/migration-guides/migrate-to-vitest-plugin/). Configure it with
  `cloudflareTest({ wrangler: { configPath: "../wrangler.jsonc" } })` in
  `worker/vitest.config.ts`. Apply migrations per test file with `readD1Migrations()` from
  `@cloudflare/vitest-plugin/config` (Node side) and `applyD1Migrations(env.DB, migrations)` from
  `cloudflare:test`. Drive the Worker with `exports.default.fetch()` / `.scheduled()` from
  `cloudflare:workers`, and use `createScheduledController()` for the cron
  (…/vitest-integration/test-apis/).
- **Version constraint found**: `@cloudflare/vitest-plugin@1.3.3` (latest) has peer
  `vitest ^4.1.0`, and so does `@cloudflare/vitest-pool-workers@0.22.0`. The repository runs
  `vitest 5.0.2`. Both cannot be satisfied in one package. Decision: make `worker/` a pnpm
  workspace package (`pnpm-workspace.yaml` gains `packages: ["worker"]`) with its own
  devDependencies `vitest@4.1.11` (the `V4` dist-tag) and `@cloudflare/vitest-plugin`. The root
  keeps `vitest 5.0.2` for Astro and unit tests. There is still one package manager and one
  lockfile (Technology Constraints).
- **Rejected**: downgrading the whole repository to Vitest 4 (regresses the other features'
  tooling and invites merge conflicts); forcing the plugin onto Vitest 5 with peer overrides
  (unsupported; failures would be hard to trace).
- **Wrangler alignment**: the plugin depends on `wrangler 4.144.0` exactly. The root
  devDependency moves from 4.143.0 to the same version, so the repository runs one Wrangler.
  pnpm's `minimumReleaseAge` is in force (see the existing `minimumReleaseAgeExclude` list). If a
  chosen version is newer than the release-age window, implement either picks the newest older
  pair that still matches, or adds an exact `minimumReleaseAgeExclude` entry as the file already
  does. It never loosens the setting globally.
- **Types**: generate `Env` with `wrangler types` (the Workers best practice: "never hand-write
  binding interfaces"). Output goes to `worker/worker-configuration.d.ts` (committed). `verify`
  runs `wrangler types --check` so the file cannot drift from `wrangler.jsonc`. No
  `@cloudflare/workers-types` package is added: `wrangler types` also emits the runtime types
  for the configured compatibility date.

## R6. Spam protection: Turnstile (server-verified) plus the `website` honeypot

- **Decision**: Turnstile widget in **managed** mode, rendered **explicitly and late**: the form
  island loads `https://challenges.cloudflare.com/turnstile/v0/api.js?render=explicit` on the
  first focus or input in the form, then calls `turnstile.render()` with
  `appearance: "interaction-only"`, `action: "contact"` and the site key. The Worker calls
  `https://challenges.cloudflare.com/turnstile/v0/siteverify` with the secret, the token,
  `remoteip` (from `CF-Connecting-IP`) and an `idempotency_key` equal to the submission ID. It
  accepts only when `success` is true, `action === "contact"` and `hostname` equals the request
  URL's hostname.
- **Rationale**: Turnstile is the constitution's named spam protection. "Loaded as late as
  possible" is Principle V. Loading on first interaction keeps api.js and its iframe out of the
  page-load budget (10 KB JS, 100 KB total in `tests/e2e/budget.spec.ts`). The hostname and
  action checks stop tokens minted on another site that uses the same key.
- **CSP**: Turnstile needs `script-src https://challenges.cloudflare.com` and `frame-src
  https://challenges.cloudflare.com` (…/turnstile/reference/content-security-policy/). These are
  added **on the contact page only**, with Astro's CSP runtime API in the contact form component
  (`Astro.csp?.insertScriptResource("https://challenges.cloudflare.com")` and
  `Astro.csp?.insertDirective("frame-src https://challenges.cloudflare.com")`;
  docs.astro.build/en/reference/api-reference/#csp). This leaves the site-wide CSP in
  `astro.config.mjs` and `public/_headers` unchanged, which avoids conflicts with the parallel
  features.
- **Hostnames**: a Turnstile hostname "will work on that exact hostname and all of its
  subdomains"; the Free plan allows 10 per widget (…/turnstile/concepts/hostname-management/).
  The widget lists `doncoleman.ca` (which covers `new.doncoleman.ca`) and
  `drc-dev.workers.dev` (covering `*-dcc-web-preview.drc-dev.workers.dev`). The docs do not say
  whether a `workers.dev` hostname is accepted. If the dashboard refuses it, the fallback is
  written into the walkthrough: the **preview** build variables and secrets use Turnstile's
  documented always-pass test pair, so previews keep working with spam protection off. Previews
  carry `noindex` and are not linked anywhere, and the preview database is separate and pruned.
- **Honeypot**: an input named `website`, visually hidden, with `tabindex="-1"`,
  `autocomplete="off"` and `aria-hidden="true"` on its wrapper (ported from Flux). When it is
  filled, the Worker returns the normal success response without Turnstile verification or any
  D1 access (FR-011).
- **Site key delivery**: `PUBLIC_TURNSTILE_SITE_KEY` is declared with Astro's typed environment
  schema (`env.schema`, `envField.string({ context: "client", access: "public" })`;
  docs.astro.build/en/guides/environment-variables/#type-safe-environment-variables). It is set
  as a Workers Builds **build** variable on both connections. The schema default is the
  always-pass test sitekey **only when `WORKERS_CI` is not `"1"`**, so local builds and GitHub
  Actions work without setup, while a Workers Builds build with the variable missing fails
  instead of shipping a test key to production.
- **Alternatives considered**: invisible-only Turnstile (no fallback path for visitors who need
  interaction); rendering on page load (breaks the budget); the Workers Rate Limiting binding as
  the only defence ("per location and approximate", rejected in the technical direction).

Superseded by #89 (2026-10), Turnstile test keys: the Worker accepts a verdict made with a
Turnstile testing key only when `ALLOW_TURNSTILE_TESTING` is exactly `"true"`. That variable is set
only in `env.preview.vars` and by the e2e server's `wrangler dev --var ALLOW_TURNSTILE_TESTING:true`
(the env file only supplies names listed in `secrets.required`); production has no value, so it
rejects a testing-key verdict with `422 turnstile_failed`. The preview fallback above still
works because preview sets the variable.

## R7. Rate limiting: exact counts from D1 by salted IP hash

- **Decision**: `ip_hash = hex(HMAC-SHA-256(key = IP_HASH_SALT, message = CF-Connecting-IP))`,
  computed with Web Crypto. Before inserting, one indexed query counts that sender's stored
  messages in the last hour and the last 24 hours:
  `SELECT COUNT(*) AS day, SUM(received_at >= ?2) AS hour FROM messages WHERE ip_hash = ?1 AND received_at >= ?3`.
  Refuse with 429 when `hour >= 3` or `day >= 5`. A missing `CF-Connecting-IP` hashes the
  literal `unknown`, so such requests share one bucket (fail closed). A D1 error fails closed
  with 503; Flux's "fail open" is not carried over.
- **Rationale**: exact everywhere (technical direction). HMAC with a secret key is a salted hash
  that cannot be reversed by hashing all 2^32 IPv4 addresses without the key (Principle VII:
  "Store only a salted hash"). The `(ip_hash, received_at)` index means the query reads at most
  the sender's rows from the last 24 hours, which is at most 5 because of the limit itself.
- **Fingerprint lifetime**: the rate-limit query never looks further back than 24 hours, so the
  daily cron sets `ip_hash` to NULL on rows older than that (spec FR-015). The column is
  nullable for that reason; NULLs are never counted.
- **Scope note**: only stored messages count. Refused attempts are not stored, so they do not
  count towards the limit. Turnstile carries that load, and every refused attempt still costs at
  most one D1 read (R10).

## R8. Idempotency and double submission

- **Decision**: the island generates `submission_id = crypto.randomUUID()` once per form fill
  and sends it with each attempt. It is regenerated only after a success. The Worker uses it as
  the primary key. After validation, and **before** Turnstile, the Worker does a primary-key
  lookup: if the ID exists, it returns the success response without verifying or storing
  anything. The insert uses `INSERT … ON CONFLICT(id) DO NOTHING`. The island also disables Send
  while a request is in flight.
- **Rationale**: Turnstile tokens are single use, so a double-click's second request would
  otherwise fail siteverify and show a false error even though the first request succeeded. The
  lookup costs one row read.

## R9. Retrieval: bearer token, two operations, cursor pagination

- **Decision**: `GET /api/messages/new?limit=&after=` lists new messages oldest first, with an
  opaque cursor `(received_at, id)`. The default page size is 50 and the maximum 100.
  `POST /api/messages/{id}/read` marks one message as read. Authorization comes first for every
  `/api/messages*` request: the Worker compares SHA-256 digests of the presented and stored
  tokens with `crypto.subtle.timingSafeEqual`. A missing or wrong key gets 401 with an identical
  body for every path and method, so it reveals nothing. With a valid key, other methods get
  405 and unknown paths 404. Details are in [contracts/retrieval-api.md](./contracts/retrieval-api.md).
- **Rationale**: FR-020–FR-024. Timing-safe comparison is a Workers best-practice rule ("Direct
  string comparison for secret values" is a listed anti-pattern). Cursor paging satisfies "all
  of them, in a bounded number of requests" without the offset scans that would grow row reads.
- **Alternatives considered**: Cloudflare Access service tokens in front of `/api/messages*`
  (first-party, but Access applies to zone hostnames, not `workers.dev` previews, and adds a
  second policy surface for two endpoints; a Worker-checked bearer token is what the technical
  direction prescribes); Secrets Store (not needed for three per-Worker secrets).

## R10. Free-plan capacity and cost (Principle IX)

Limits (fetched 2026-09-29): Workers Free has 100,000 requests/day, 10 ms CPU per request and
5 Cron Triggers per account (…/workers/platform/limits/). D1 on Workers Free has 5,000,000 rows
read/day, 100,000 rows written/day, 5 GB storage, 500 MB per database and 10 databases, and "if
you exceed … you will not be able to run queries … No charges apply"
(…/d1/platform/pricing/, …/d1/platform/limits/). Workers Builds Free has 3,000 build
minutes/month and 1 concurrent build (…/ci-cd/builds/limits-and-pricing/). Turnstile is free,
with up to 10 hostnames per widget.

**Row costs per operation** (D1 counts every row an index or table scan touches; each indexed
column adds a written row per insert/update/delete):

| Operation | Rows read | Rows written |
|---|---|---|
| Honeypot hit, validation failure, bad origin | 0 | 0 |
| Duplicate submission (PK lookup) | 1 | 0 |
| Turnstile failure | 1 (PK lookup) | 0 |
| Rate-limited submission | 1 + ≤5 | 0 |
| Accepted submission | 1 + ≤5 | 5 (table + PK index + 3 secondary indexes) |
| List new (per page) | ≤ page size + 1 | 0 |
| Mark read | 1 | ≤ 3 (row + status index entry) |
| Retention (per deleted row) | 1 | 5 |
| Fingerprint clearing (per row, once) | 1 | ≤ 3 (row + ip index entry) |

**Expected usage** (generous: 20 accepted messages/day, which is far above a consulting site's
real volume; an assistant polling every 15 minutes; 100 bot attempts/day):

| Metric | Per day | Free limit | Share |
|---|---|---|---|
| Worker requests (`/api/*` + cron) | 20 + 100 + 96 polls + 20 mark-read + 2 cron ≈ 240 | 100,000 | 0.24% |
| D1 rows read (prod + preview) | 20×6 + 100×1 + 96×(≤21) + 20×1 + 20 ≈ 2,300 | 5,000,000 | < 0.05% |
| D1 rows written | 20×5 + 20×3 + 20×5 (retention) + 20×3 (fingerprint clearing) = 320 | 100,000 | 0.32% |
| Storage (12 months, ≤ 10 KB per row incl. indexes) | 7,300 rows ≈ 73 MB worst case | 500 MB/db, 5 GB total | < 15% |
| Cron Triggers | 2 (one per Worker) | 5 per account | 40% |
| D1 databases | 2 | 10 | 20% |
| Workers Logs events | ≈ 240 | 200,000 | ≈ 0.1% |

**Worst case, abuse**: an attacker can at most use up the Worker's 100,000 daily requests. Even
if every request reached the deepest read path (≤ 7 rows), that is ≤ 700,000 rows read, 14% of
D1's daily read limit. Writes need a passing Turnstile token per stored row, plus the 5-per-day
per-IP limit, so the 100,000 writes/day limit would need about 20,000 human-verified submissions
a day. On the Free plan, going over any limit returns errors (Workers returns 429; D1 refuses
queries). It never bills.

**Builds**: previews move from `dcc-web` to `dcc-web-preview`, so a branch push still triggers
one build. A push to `main` now triggers two (production plus preview). At a generous 100
pushes a month and about 4 minutes per build, that is about 400–800 minutes, under 3,000.

**Result: expected monthly cost $0.** This assumes the Cloudflare account stays on the Workers
**Free** plan. On Workers Paid, D1 overage would bill instead of erroring. The walkthrough
states this assumption, and a change of plan would be its own major change.

## R11. Retention: daily cron, 12 calendar months, indexed delete

- **Decision**: `triggers.crons: ["17 3 * * *"]` (03:17 UTC daily, off the hour to avoid
  platform peaks) in both environments. The `scheduled` handler deletes rows with
  `received_at < cutoff`, where `cutoff` is the scheduled time minus 12 calendar months (UTC).
  It deletes in batches of 500 (`DELETE … WHERE id IN (SELECT id … LIMIT 500)`), looping until
  fewer than 500 rows go. It logs only `{"event":"retention","deleted":n}`.
- **Rationale**: FR-018 ("at least once a day, whatever their status"). The
  `idx_messages_received` index keeps the delete proportional to expired rows. Batching keeps
  each statement small, well under D1's 50-queries-per-invocation Free limit for any realistic
  backlog. The cutoff is computed from `controller.scheduledTime`, so tests control time
  exactly.

## R12. The contact page: MDX content plus a registered `ContactForm` section island

- **Decision**: `src/content/pages/contact.mdx` holds the page copy (intro and the short
  "what happens to your information" note linking to `/privacy-policy/`) and places
  `<ContactForm />`. `ContactForm` is added to the closed section registry
  (`src/components/sections/index.ts` and `schemas.ts`). The component renders the full form
  markup statically, so it is readable with no JavaScript, plus a `<noscript>`-independent
  notice that sending needs JavaScript. The notice is shown by default and hidden by the island
  when it starts. The behaviour lives in a processed `<script>` in the component, which Astro
  bundles and hashes into the CSP automatically
  (docs.astro.build/en/guides/client-side-scripts/). `/contact/` is removed from
  `futureDestinations` in `src/config/navigation.ts`, so the existing fixed Contact entry
  (position 7) now resolves.
- **Rationale**: Principle VI keeps public copy in content files, and the section registry is
  the established extension point (docs/design-source.md "Content structure"). The page stays
  prerendered (Principle V). The only scripts it loads are the island and, after interaction,
  Turnstile (FR-009).
- **Project context**: the island reads `?project=` with `URLSearchParams`. It trims the value,
  removes control characters and cuts it to 100 characters, then shows it with `textContent`
  only ("About: <project>") and puts it in a hidden input. Any markup is inert (FR-004,
  User Story 5).
- **Ported from Flux** (`partials/ui-contact-form.hbs`, `assets/js/contact-form.js`): the
  two-column name/email grid, the email icon, the textarea, the consent checkbox wording with
  `/privacy-policy/`, the error box and the success panel, and the Tailwind classes.
  Adjustments: the Ghost member pre-fill, the Supabase client and the auth bridge are removed.
  An optional organization field is added. `maxlength` values come from the shared rules
  module, and the message limit becomes 5,000 (Flux's textarea said 1,000; its server said
  5,000). Errors are tied to fields with `aria-describedby` and `aria-invalid`. One
  `role="status"` live region carries confirmation and general errors. Focus moves to the
  success heading or to the first invalid field. The "at least 10 characters" rule is dropped,
  because the spec sets no minimum. `console.error` of error objects is dropped (FR-016).
  Colour pairings are checked against the WCAG 2.2 AA adjustments table in
  `docs/design-source.md`.
